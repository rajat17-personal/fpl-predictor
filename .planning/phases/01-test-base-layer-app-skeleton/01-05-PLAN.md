<objective>
Complete the app shell: all eight routes reachable, each isolated behind its own error boundary, with
the loading, error, empty, placeholder, and not-found states the UI-SPEC contract specifies — and
held-out tests for the three states the UI-SPEC explicitly marked as needing them.

Plan 01-04 proved one route can reach the backend. This plan turns that into a navigable shell. The
load-bearing structural decision is per-route `errorElement`: without it, one page's failed
`fixtures.json` fetch unmounts the whole tree and takes the nav down with it, which is exactly the
failure the vanilla multi-page site cannot have and a single-page app can. React Router 7 has a
native mechanism for this, and the UI-SPEC already specifies it.

Purpose: give Phase 2 eight working route files to fill in, and close the three
`resolved (backstop)` rows the UI-SPEC signed off on for *this* phase — deferring them to Phase 4's
Playwright suite would leave approved design commitments unverified for three phases, and Playwright
is a different tier of test anyway.
Output: `router.tsx` with 8 routes plus a catch-all, five shell components, and three backstop tests.

**Explicitly out of scope** (deferred by the UI-SPEC's own Scope Note): per-page content, tables,
sort/filter UI, the FDR green-to-red ticker, the dark-mode *toggle* (the tokens exist from plan
01-04; the switch is Phase 2 UIX-02), and everything pitch-related (Phase 3).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| failing route → application shell | A thrown render or fetch error in one route can unmount the whole React tree, including the nav, unless a boundary contains it |
| thrown Error / HTTP response → rendered DOM | Error text carries internal paths, statuses, and stack frames that reach the user's screen if rendered directly |
| user-controlled URL path → route resolution | An arbitrary path must resolve to a defined 404 state rather than an unhandled match failure |
