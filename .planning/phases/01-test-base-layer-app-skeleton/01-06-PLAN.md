<objective>
Close UAT gap **G-01-3**: on wide desktop viewports (~1720px) the app-shell header renders
full-bleed while the main element and the footer are capped at 68rem, so the brand+nav sit
left-clustered against a large empty gutter and the fixed 14px nav text reads stranded and
undersized.

The diagnosis (`.planning/debug/nav-text-not-responsive.md`) is conclusive and it eliminates the
obvious-but-wrong fix: this is **not** a typography defect. The vanilla parity source
(`web/assets/style.css:74`) uses a flat, non-responsive `0.88rem` nav font at every breakpoint
and still reads correctly at 1720px - because `header.site` is nested inside
`.wrap { max-width: 68rem; margin: 0 auto }`. The React rebuild dropped that containment on the
header only. The fix is therefore layout containment; adding responsive font-size utilities
would violate the UI-SPEC's fixed Label token and break vanilla parity.

Purpose: restore the UI-SPEC "Layout frame" contract (`Content max-width | 68rem (1088px),
centered` plus `Page horizontal padding | 16px`) uniformly across all three chrome sections, and
lock it with a regression test so the omission cannot recur silently.

Output: a corrected `PageShell.tsx`, a new `PageShell.test.tsx` containment-parity test, and a
recorded handoff of the true pixel-width assertion to Phase 4 (E2E-01).

**Tracer-first opt-out (deliberate):** this plan intentionally has no tracer task. The end-to-end
architecture of this shell was already proven by the 01-04 tracer (Vite + React Router + TanStack
Query dev seam) and expanded by 01-05 (all 8 routes, error boundaries). This is a single-file
containment correction on that proven skeleton - a thin vertical slice here would restate what is
already committed and green, adding no information.
</objective>

**One deliberate extension beyond the literal gap text, and why it is not scope creep:** item 1
says "keep border/**padding** full-bleed on outer header". Taken literally - leaving the 16px
gutter on the outer header element and putting only the centering and the cap on the inner
wrapper - the header's *content* would span the full 1088px cap while the main element's content
spans 1088px minus its own 16px gutters (1056px). That lands the nav 16px wider on each side than
the page content directly beneath it: the stranded-nav complaint is fixed but replaced by a
visible new misalignment. Vanilla does not do this - its `.wrap` owns both the 68rem cap and the
16px gutter, and `header.site` / `footer.site` sit inside it, so header content and page content
both span 1056px and align exactly. Task 1 therefore moves the horizontal padding onto the
contained inner wrapper (the border stays full-bleed on the outer element, exactly as item 1
requires) and applies the same one-line correction to the footer's inner paragraph, which has the
identical defect today. This is the same single concern - chrome containment geometry - in the
same single file, not a second feature.

Nothing is simplified, staged, or reduced to a "v1": the gap is closed in full this plan.
