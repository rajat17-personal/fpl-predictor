<objective>
Complete the API safety net: the two endpoints that reach the FPL API over real HTTP, the auth stub
in all three of its modes, and the concurrency race that today is only observable in production.

Plan 01-02 established the seam and proved it on the endpoints that need nothing but `_state`. This
plan covers the harder half. `_fetch_team()` and `_free_transfers()` call `requests.get()` directly
against `config.FPL_API` — not through an importable function like `_load_live` — so mocking them
needs URL-level interception. `require_key()` is the single choke point the whole monetisation path
will eventually be swapped through, and it currently has exactly one assertion anywhere in the repo.
And `_refresh()` clears `_solve_cache` inside `_lock` while `solve()` reads and writes that same dict
outside it — a race that a sequential loop of `TestClient` calls cannot reproduce, because
overlapping requests are what create it.

Purpose: make an FPL-contract regression, an auth regression, and a concurrency regression each fail
a test instead of failing a user.
Output: `/api/team` and `/api/rate` contract tests, three-mode `require_key` coverage, and a
repeatable real-thread concurrency test.

**Decision recorded** (`01-RESEARCH.md` Open Question 2): the concurrency test runs in-process
against `TestClient`, not against a subprocess `uvicorn`. Starlette dispatches each sync handler
through `anyio.to_thread.run_sync`, so `TestClient` driven from a `ThreadPoolExecutor` produces
genuine thread-level overlap on the actual `_lock` / `_state` code paths. Escalate to a real
subprocess only if a race is suspected from production logs that this cannot reproduce.
</objective>
