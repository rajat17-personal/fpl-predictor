## Environment facts established at planning time

- There is **no container runtime** on this machine (`docker`, `podman`, `buildah` and the docker
  socket are all absent), so the image build and the smoke test cannot run locally.
- There is **no `gh` CLI** and no `jq`, so the executor cannot query GitHub's API for run status or
  package listings even after the push.
- There is **no git remote** configured (`git remote -v` is empty).

Together these are why the closing gate is a human checkpoint that asks the developer to report what
they observed, rather than an automated step that reads it back. That is also exactly what D-14
specifies.

  <action>
    Create `scripts/preflight.sh`, executable, following this repository's shell conventions exactly:
    `#!/usr/bin/env bash`, a purpose comment block explaining that this runs the same verification
    sequence the CI workflow's `lint-build` and `test` jobs run so a red pipeline is discovered before
    a push rather than after, a `Usage:` line, `set -euo pipefail`, and `cd "$(dirname "$0")/.."`.

    Run these gates in order, each announced with a bracketed `[preflight]` status line naming the gate,
    and each failing with a `FAILED:` line that names the gate and what to do about it:

    1. **Hash-locked environment.** Create a venv from the interpreter named by an `PREFLIGHT_PYTHON`
       environment seam (default `python3`, so the script works on a CI runner too, with the developer
       setting it to the conda 3.14 interpreter locally — the same seam convention `E2E_PYTHON` uses in
       the Playwright config). Install both locks into it with
       `pip install --require-hashes -r requirements.txt -r requirements-dev.txt`. Remove the venv on
       exit via a trap.
    2. **Lint.** Run `ruff check .` from that venv.
    3. **Frontend build.** Run `npm --prefix frontend ci` then `npm --prefix frontend run build`. Then
       assert `frontend/dist/index.html` and `frontend/dist/404.html` both exist, failing with a message
       naming whichever is missing — this is the exact guard the CI `test` job carries and the reason
       Phase 4's review flagged the ordering.
    4. **Backend tests.** Run `python -m pytest` from the venv, at the repository root, with no extra
       flags so `pytest.ini` governs. Use the `-m` form; it is what puts the repository root on the
       import path.
    5. **Frontend tests.** Run `npm --prefix frontend test`.
    6. **Workflow hygiene.** Assert that every `uses:` line across all three files in
       `.github/workflows/` carries a 40-character commit SHA, by counting `uses:` lines and
       SHA-pinned `uses:` lines and comparing; echo both counts so the check is visibly non-vacuous.
       Assert no workflow carries a `schedule` trigger. Assert no tracked file contains a personal email
       address or a credential-shaped literal, echoing the number of tracked files scanned.
    7. **Container.** If a container runtime is available, build the image and run
       `scripts/smoke_test.sh` against it. If none is available, print a clearly-labelled
       `[preflight] SKIPPED` line naming the container gate and stating that it will be exercised by the
       CI `image` job — a skip, announced, is honest; a silent pass is not. A skipped container gate must
       not change the script's exit status, and the final summary must state how many gates ran and how
       many were skipped.

    End with a summary block listing each gate and its result, then `PREFLIGHT PASSED` on success. Never
    swallow a failure to keep going: the first failing gate stops the script.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local working tree → GitHub | The first push makes every tracked file permanently visible to anyone with repository access |
| pull request → default branch | A merge is what makes the publish job reachable and the `latest` tag movable |
| GHCR package listing → future deployments | The published image becomes the input to next milestone's deploy story |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-05-01 | Information Disclosure | the first push | high | mitigate | `scripts/preflight.sh` re-runs the tracked-file scan for personal emails and credential literals with a reported file count immediately before the checkpoint; the repository is created private per D-13 |
| T-05-05-02 | Tampering | the `latest` tag on the default branch | high | mitigate | Branch protection requires the four verification jobs to pass before a merge, so a red run cannot reach the publish job and cannot move `latest` |
| T-05-05-03 | Spoofing | push authorship | medium | accept | The developer pushes under their own GitHub credential from their own machine; no automation in this phase holds a push credential, and none is created |
| T-05-05-04 | Elevation of Privilege | credentials held by this agent | high | mitigate | No `gh` CLI is installed, no remote is configured, and no token is requested or stored; every network write in this phase is performed by the developer |
| T-05-05-05 | Denial of Service | GHCR private-tier storage | low | accept | Reported image size is captured at the checkpoint so a retention policy can be sized before the next milestone rather than discovered at the 500MB ceiling |
</threat_model>
