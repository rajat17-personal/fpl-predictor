# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Note

This phase (PITCH-01..04, UI-07, UIX-01, UIX-03) **extends** the Phase 1/2 app-shell and token
contracts (`01-UI-SPEC.md`, `02-UI-SPEC.md`) — it does not restart them. All carried tokens,
the spacing scale, the `68rem` containment geometry, `PageShell`, the GW banner, the theme
toggle, `StatusFlag`'s accessible popover pattern, and `bandCell.ts`'s band-geometry math stay
unchanged unless a row below explicitly extends them. This document builds the eighth and final
route (`/team`), replacing its Phase 1/2 placeholder with real content for the first time.

**Critical framing (from `03-CONTEXT.md`):** unlike Phase 2, this is mostly *new UI design*, not
parity porting — vanilla has no pitch. Only the rate/plan flows (`web/team.html`) have vanilla
behavior and copy to preserve verbatim (D-19). Everything pitch-shaped (formation rows, player
cards, kit SVGs, tabs, lock/exclude, solve UX, the rate diff, chip timeline) is this phase's own
design, built to the official FPL app's visual grammar as the north star, not a vanilla port.

**Explicitly out of scope for this phase's UI (do not build):** E2E coverage of these flows
(Phase 4), any change to `web/data/*.json` (VC/formation/band derivation happen client-side per
D-08), a full 15-player "ideal squad" diff (the API only returns a single best move — see
`03-RESEARCH.md` Pitfall 1), payment/auth UI (`PAID-*`, v2).

## Pitch Design (PITCH-02, UI-07, D-05, D-07)

### Surface

- FPL-style green pitch: two-stop vertical gradient (`--color-pitch-1` top → `--color-pitch-2`
  bottom), rounded corners matching the card-radius convention already in use, white markings
  (`--color-pitch-line`) drawn as absolutely-positioned/inline-SVG lines: one center circle, two
  penalty-box outlines (top and bottom edge), one halfway line. Markings are decorative
  (`aria-hidden="true"`) — they carry no information a screen reader needs.
- Formation rows sit on the pitch surface (GK / DEF / MID / FWD, top to bottom); the bench strip
  sits **below** the pitch surface in a separate, non-green container (`--color-surface`
  background, per the established secondary-surface role) — visually and semantically distinct
  from the starting XI, matching the official FPL app's convention.

### Layout — CSS Grid, verified 5-column ceiling (D-07)

- One shared grid definition for every formation row: `grid-template-columns: repeat(5,
  minmax(0, 1fr))`. This does **not** change column count at any viewport width — D-07 requires
  the full formation to "always fit," which this contract satisfies by keeping the column count
  fixed and shrinking card content instead of reflowing. GK's row uses the same 5-column grid
  with the single GK card centered (`grid-column: 3 / 4`); rows with fewer than 5 starters (e.g.
  a 3-DEF row) center their cards within the row via `justify-content: center` on the row
  container, not by changing `grid-template-columns`.
- Row gap: `--spacing-sm` (8px) at ≥480px viewport width; `--spacing-xs` (4px) below 480px
  (spacing-scale exception, same category as Phase 2's FDR cell `min-width`).
- Bench strip: always exactly 4 cards (`15 − 11`, verified against `config.SQUAD_SIZE`/
  `POSITION_QUOTA` per `03-RESEARCH.md`), same 5-column grid (4 cards + 1 empty/spacer cell,
  or a 4-column grid dedicated to the bench — either is acceptable; the constraint is "never
  wider than the widest formation row above it").
- Formation label: rendered once above the pitch, e.g. **"3-5-2"**, derived via
  `deriveFormation()` (see `03-RESEARCH.md` Pattern 1) — never hand-entered, never fetched.

### Mobile shrink behavior (UI-07, D-07)

- Card content (kit SVG, name, price, xP, range line) scales down via a single "compact" CSS
  variant applied below a `640px` viewport width (Tailwind's `sm` breakpoint) — not via
  reflowing the grid.
- Name: single-line `truncate` (ellipsis) at every breakpoint; full name available via the
  card's tap-popover detail panel (D-13), never a bare `title` attribute (accessibility parity
  with `StatusFlag`'s D-09 pattern).
- Price and xP value: always visible, never truncated or hidden — these are the two numbers a
  user needs to evaluate a card at a glance.
- Range line (p10–p90): always visible down to 400px viewport width. **Below 400px** (component-
  sizing exception, same category as the FDR ticker's 56px minimum in Phase 2), the range line
  is replaced by a tap-reveal affordance reusing `StatusFlag`'s D-09 accessible popover pattern —
  tapping the xP value opens a small popover showing the full `{p10}–{p90}` range and the
  verbatim `bandTooltip()` copy. This is the only place D-06's "no interaction required" rule
  has a documented, viewport-gated exception.

### GK differentiation (A3, Claude's Discretion — resolved here)

Goalkeepers use one **fixed, club-independent** kit scheme, never the outfield club colors:
primary `#3A3A3A` (charcoal), secondary `#EAB308` (amber trim), pattern `plain`. Standard
football convention (GK shirt visually distinct from outfield); applied to every GK card
regardless of team.

### Unmapped-club fallback (defensive only, not a substitute for map completeness)

If a `team_short` is encountered that is **not** in `kitMap.ts` (a future data change, not any
club in the current verified list), render a neutral fallback kit — primary `#9CA3AF`,
secondary `#4B5563`, pattern `plain` — and log a dev-only console warning naming the missing
code. This is a safety net for future data drift, not a way to leave any of the 20 known clubs
unmapped; `kitMap.test.ts` fails if any club in the current list resolves to the fallback.

## Player Card (PITCH-02, UIX-01, D-06, D-08)

### Layout (top to bottom)

1. Kit SVG (club/GK colors per above), with C/VC badge overlaid on the top-right corner when
   applicable.
2. Name — single-line `truncate`, Label size (14px/400, IBM Plex Sans).
3. Price + xP — one line, Numeric modifier (IBM Plex Mono, `tabular-nums`, Label size):
   `£{price_m.toFixed(1)} · {xp.toFixed(1)}`.
4. Range line (D-06) — always visible (down to the 400px exception above), Numeric modifier,
   smaller visual weight than the price/xP line but same token size (no new size — Label is the
   floor): `{p10.toFixed(1)}–{p90.toFixed(1)}`, geometry/tooltip sourced from `bandGeometry()`/
   `bandTooltip()` (`bandCell.ts`, reused verbatim per Don't-Hand-Roll).

### C/VC badges (D-08)

- **Captain (C):** filled circle, `--color-accent` background, white/high-contrast "C" glyph,
  positioned top-right of the kit SVG. Sourced directly from `squad.json`/API response's
  `captain: true` row — no derivation needed.
- **Vice-captain (VC):** outlined circle, `--color-accent` border, `--color-accent-ink` "V"
  glyph, transparent fill, same position (never both C and VC on one card — mutually exclusive
  by construction). **Derived client-side** via `deriveViceCaptain()` (`03-RESEARCH.md` Pattern
  2) — the starter with the highest `xp_capt` (joined from `xp_table.json` by `player_code`) who
  isn't the captain. Card renders no VC badge at all if the join yields `null` (e.g. `xp_capt`
  absent for every starter) — never a placeholder badge.

### Lock/Exclude badges (D-13)

- **Locked:** small padlock icon (`Lock`, lucide-react) badge, bottom-left of the card,
  `--color-accent-ink` on `--color-accent-bg`, `aria-label="Locked — always included in solve"`.
- **Excluded:** small `X` icon badge, same position, `--color-bad` on a light destructive-tint
  background (reuse the existing `--color-bad` role, no new token), `aria-label="Excluded from
  solve"`.
- A card can carry at most one of Locked/Excluded at a time (tapping the other option in the
  popover replaces, doesn't stack).

### Solve-result badges (D-16)

- **IN:** small badge, top-left, `--color-accent` background, white "IN" text,
  `aria-label="New signing this transfer"` — rendered only on cards present in a post-solve
  `squad[]` response that were not in the pre-solve loaded squad.
- No "OUT" badge on the Squad-tab pitch itself (outgoing players simply disappear from the
  re-rendered pitch — D-16's "pitch re-renders in place"); the "out" treatment is specific to
  the **Rate tab's diff** (D-18, see below), which is a different view with a different purpose.

### Interaction (D-13)

Tapping/clicking a card opens an action popover (reusing `StatusFlag`'s D-09 open/close state
machine — outside-click and `Escape` dismiss, 44px touch targets), with `role="menu"` semantics
(distinct from `StatusFlag`'s `role="tooltip"` per `03-RESEARCH.md` Pattern 6, since this
popover contains actionable items, not just a read-only tooltip):

| Item | Behavior |
|------|----------|
| Player detail | Non-interactive header row: full name, team, status flag/news if applicable, ownership % (from `xp_table.json`'s join) |
| Lock in squad | `role="menuitem"` button — marks `player_code` as locked; clears any existing exclude on that card |
| Exclude from squad | `role="menuitem"` button — marks `player_code` as excluded; clears any existing lock |
| Clear | `role="menuitem"` button — removes lock/exclude mark; only rendered when the card currently carries one |

## Team Page Structure (PITCH-03, D-09..D-12)

### Tabs

One `/team` route, three tabs: **Squad** (default) / **Rate my team** / **Chips**. Tab bar
styled consistently with the existing pill/segmented-control family (GW chip, theme toggle) —
`--color-surface` background, `--color-line` border, active tab gets `--color-accent-bg`
background + `--color-accent-ink` text (same active-state token pairing as the nav link and
theme toggle, for visual consistency across the whole app). Each tab is a `role="tab"` /
`role="tabpanel"` pair (standard ARIA tabs pattern) — no new accessibility pattern needed beyond
what's already established.

### URL state (D-11)

`?entry=` (numeric FPL team ID) + `?tab=` (`squad` default / `rate` / `chips`), synced via React
Router 7's `useSearchParams()` (no custom hook — Don't Hand-Roll). An `?entry=` deep link loads
that squad on the Squad tab (or whichever `?tab=` is also present); a `?tab=rate` deep link with
an `?entry=` present auto-runs the rate fetch (D-20's on-demand exception). Locks, excludes, and
solve results are never written to the URL (ephemeral, Phase 2 D-07).

### Nav rename (D-12) — deviation ledger entry

`PageShell`'s `NAV_LINKS` entry for `/team` changes label from **"Rate my team"** to **"My
team"** — the page outgrew its vanilla name (it now hosts the pitch, solver, rate, and chips,
not just rating). One-line ledger entry required (see Deviation Ledger Additions).

### Default Squad tab content (D-10, Claude's Discretion resolved)

The default Squad tab (no `?entry=` present) renders `squad.json` — the model's recommended
squad of the week — labeled **"Model squad · GW{meta.gw}"** above the pitch, sourced from the
already-fetched `meta.json` (shared `PageShell` query, no new fetch). **View-only**: no
lock/exclude/solve controls on the default model-squad view (per `03-RESEARCH.md`'s
recommendation — the loaded-team flow below already fully covers the solve/lock/exclude surface
once a real entry ID is loaded, keeping this phase's scope aligned with its four success
criteria). An "Load your own team" entry-ID control sits below the pitch, inviting the user to
switch into the interactive flow.

### Loaded-team flow (once `?entry=` is present)

- Entry-ID input: `type="number" min="1"`, placeholder `"Team ID, e.g. 6980093"` (D-10 — 6980093
  is example text only, never auto-submitted), `aria-label="FPL team ID"`.
- Primary CTA: **"Load team"** — calls `/api/team/{entry}`, replaces the pitch with that squad
  (banner updates to `"{team_name} · GW{meta.gw}"`, with a small "Change team" link to clear
  `?entry=` and return to the default model-squad view).
- Once loaded, the pitch is interactive: tap-to-lock/exclude (see Player Card) and the solve
  controls (below) become available.

## Solver UX (PITCH-03, D-13..D-17)

### Solve controls (D-14 — essentials only)

A compact control row above/beside the pitch, visible only once a team is loaded:

| Control | Type | Bounds | Default |
|---------|------|--------|---------|
| Free transfers | Number input | 0–5 (mirrors `SolveRequest`'s server-side bound) | Prefilled from the API's estimate (`/api/rate`'s `free_transfers` field or `/api/team`'s equivalent), editable |
| Max transfers | Number input | 0–15 | Unset (server default — no artificial cap) |
| Plan horizon | Select | 1 / 2 / 3 / 4 / 6 gameweeks (same options as vanilla's plan horizon `<select>`) | 1 (single-GW solve) |

Mode and budget are **not** exposed — server defaults apply (D-14). Every input mirrors its
server-side `Field(ge=…, le=…)` bound as its own `min`/`max` (per `03-RESEARCH.md`'s Input
Validation note) to avoid a round-trip 422.

### Primary CTA — "Solve transfers"

Button disables while a solve is in flight (D-15). Locks/excludes are sent as `player_code`
integers only, never free-text names (Pitfall 3).

### Wait state (D-15 — inline status, honest copy)

Inline status line appears beside the (still-visible, still-rendered) pitch: **"Solving your
transfers…"** — mirrors vanilla's `"Solving your squad…"` tone exactly (same verb/ellipsis
pattern, different noun for this new one-solve interaction). If the horizon is used via the
Rate tab's Plan flow (not this control), vanilla's exact multi-GW wait copy carries over
unchanged (see Rate-my-team below) — that copy string is **not** duplicated here since Squad-tab
solves are always single-horizon (`horizon` not exposed on this control, see table above).

### Solve error copy

**"Couldn't solve: {message}. Check your inputs and try again."** — same tone/structure as
vanilla's rate-error copy (`"Couldn't rate that team: {message}. Check the ID and try again."`),
adapted for this new interaction.

### Results (D-16 — pitch updates in place)

- The pitch re-renders with the post-solve `squad[]` (branches on `SolveResult.kind`, per
  `03-RESEARCH.md` Pattern 4 — the Squad tab only ever produces `kind: "transfers"` responses
  once an entry is loaded, per the view-only default resolution above).
- A compact results bar sits below the pitch:

| Field | Format |
|-------|--------|
| Moves | `{sell.name} → {buy.name}` pairs, one per line, via `pairMoves()` ported verbatim from `web/team.html` (Don't Hand-Roll) — `"Hold"` if `buys.length === 0` |
| Hit cost | `−{4 × hits} pts in hits` if `hits > 0`, else omitted (not `"0 pts"` — vanilla omits the clause entirely when there's no hit) |
| Bank after | `£{bank_after.toFixed(1)}m` |
| XI xP | `{xi_xp}` (plus the p10–p90 range if `xi_p10`/`xi_p90` are non-null — Pitfall 2, always null-guard) |
| Captain | `{captain}` (name string from the response) |

### Reset (D-17)

**"Reset to loaded squad"** (verbatim phrase from `03-CONTEXT.md` D-17) — a secondary action
(text button or ghost-style, not competing visually with the primary "Solve transfers" CTA)
that restores the as-loaded team, clears all locks/excludes, and discards the current solve
result. Solve results are never persisted — this is purely a local-state reset.

## Rate-My-Team (PITCH-04, D-18..D-20)

### Fetch timing (D-20)

On-demand — fires when the Rate tab is opened (or immediately on mount if `?tab=rate` is the
deep-linked entry point, per D-11), then cached by TanStack Query for the session. Never fires
speculatively when the Squad tab is active.

### Tiles (D-19 — verbatim vanilla copy, four tiles)

Ported 1:1 from `web/team.html`'s `#result` tiles block — same headings, same value formatting,
same fallback logic:

| Tile | Heading | Value | Detail line |
|------|---------|-------|--------------|
| Team score | `Team score` | `{score}/100` | `best XI xP {xi_xp}{" (" + xi_p10 + "–" + xi_p90 + " in 8/10 GWs)" if xi_p10 != null else ""} vs ideal {ideal_xi_xp}` |
| Season so far | `Season so far` | `{overall_points ?? "–"} pts` | `overall rank {fmtRank(overall_rank)} · last GW {gw_points ?? "–"} pts` |
| Captain | `Captain` | `{captain}` | `best armband in your current squad` |
| Best move | `Best move` | `{sell.join(", ")} → {buy.join(", ")}` (or `"Hold"`) | `+{xp_gain} xP this gameweek` (or `"no single transfer beats your current squad"` when `best_move` is `null` — Pitfall 1/Open Question 2) |

`fmtRank(n)` — verbatim: `n == null ? "–" : n.toLocaleString()`.

### Visual diff — one pitch + swap overlays (D-18)

**Bounded by the API's actual shape (Pitfall 1 — `/api/rate` returns one best move, not a full
ideal squad):**

- The pitch renders the user's own full 15-row `xi[]` (their current best XI per the model, not
  a hypothetical) — this is real, complete data.
- If `best_move` is non-null: the one player in `best_move.sell` gets the **"out" treatment**
  (dimmed/red-tinted overlay on their existing card, `aria-label` noting "suggested transfer
  out"); the one player in `best_move.buy` renders as a **ghost/insert card** (dashed
  `--color-accent` border, `--color-accent-bg` fill, semi-transparent) positioned adjacent to
  the "out" card in the same formation row.
- If `best_move` is `null` (Open Question 2 — the "Hold" case): no overlays render at all — a
  plain pitch is self-explanatory alongside the tile copy already stating "Hold" /
  "no single transfer beats your current squad." No special-case pitch rendering needed.
- A swap-list line sits beside/below the pitch, textual: `{sell.name} → {buy.name}` with
  `+{xp_gain} xP`, or omitted entirely in the Hold case.
- **Anti-pattern (do not build):** a full 15-vs-15 "ideal squad" diff — the API has no such data
  to give (see `03-RESEARCH.md` Pitfall 1). Do not design a prop expecting an `idealSquad:
  SquadRow[]` array.

### Best-XI-for-this-GW section (D-19, verbatim heading/sub)

- Heading: **"Your best XI for GW{gw}"**
- Sub (verbatim): "Keeping your current squad (no transfers), this is the lineup and captain
  the model would field."
- Rendering: the same `<Pitch>` component (D-19 explicitly allows swapping vanilla's
  `squadCards()` list for the new pitch component here — "the pitch diff is the new
  centerpiece").

### Plan transfers flow (D-19, verbatim copy + controls)

- Heading: **"Plan transfers"**
- Sub (verbatim): "The solver plans your moves jointly over the horizon — when to move now,
  when to bank a free transfer, when a hit pays for itself. Free transfers are pre-filled with
  our estimate from your transfer history (FPL only shows the true figure to your own login) —
  correct it if the official site says otherwise."
- Controls (verbatim): Free transfers number input (`min=1 max=5`, prefilled from
  `free_transfers ?? 1`), Plan-over select (`next GW only` / `2 gameweeks` / `3 gameweeks`
  *(default)* / `4 gameweeks` / `6 gameweeks`), primary CTA **"Plan my transfers"**.
- Wait copy (verbatim, honest — D-15 discipline extends here): `"Planning {n} gameweek{s} jointly…"`
  plus, only when `hz > 1`: `" (a fresh horizon takes ~10-60s while future gameweeks are
  predicted)"`.
- Per-week output: heading `"GW{gw} {— do this now | — planned}"` (first week vs later weeks),
  a moves tile (`pairMoves()` output or `"Hold"`, transfer count, hit note, FT-carried note), a
  projected-XI tile (`xi_xp`, p10–p90 if present, captain, bank), and a collapsible `<details>`
  (open only for week one) showing that week's squad on the pitch component (replacing
  vanilla's `squadCards()` the same way as the Best-XI section above).
- Closing sub (verbatim): "Week one is the decision to act on; later weeks are the current plan
  and will re-optimise as prices, injuries and form move."
- Error copy (verbatim): `"Planning failed: {message}"`.
- Rate-fetch error copy (verbatim): `"Couldn't rate that team: {message}. Check the ID and try
  again."`

## Chip Timing (UIX-03, D-21)

### Layout — GW timeline strip

A horizontal scrollable timeline, current GW → 38, rendered as a row of GW markers (small
circles/ticks on a horizontal line, current GW visually emphasized — larger marker,
`--color-accent` ring). DGW gameweeks get an `--color-accent`-filled marker with a "DGW" badge
label; BGW gameweeks get a `--color-bad`-filled marker with a "BGW" badge label (reusing the
established green=favorable/red=risk semantics from the status-flag and price-indicator
patterns — no new color roles). Tapping/hovering a DGW/BGW marker reveals the affected clubs
(`dgw_clubs`/`bgw_clubs` from `chips.json`'s `structure[]`) via the same D-09 accessible-popover
pattern used elsewhere.
