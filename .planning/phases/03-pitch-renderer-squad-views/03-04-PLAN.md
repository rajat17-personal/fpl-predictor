solver knobs that matter, request a solve, and watch the transfers and the starting XI update on
the same pitch — with a results bar summarising the move and a reset that puts everything back.

to `/api/solve`.

server's own limits, and a `SolveResultsBar` that renders the solve outcome beneath an in-place
pitch update.
</objective>

**State.** One `useState` holding a record keyed by `player_code` with values `"locked"` or

**Handler semantics (D-13).** Setting `"locked"` on a card that is excluded replaces the exclude,
and setting `"excluded"` on a locked card replaces the lock — the two are mutually exclusive, which
matches the popover's own behaviour built in 03-01. Passing `null` clears the entry outright rather

arrays by a plain key filter.

stays view-only — it passes no `onMark`, so its cards render no popover trigger at all, which is
the resolution of the Claude's-Discretion item recorded in 03-01's summary.

**Persistence across solves (D-17).** Do not clear marks when a solve completes. A user adjusting
one lock and re-solving must not have to re-mark the other fourteen players; iterating freely is the
whole point of the interaction. The only thing that clears marks is the Reset action built in
Task 3.

**Derived request arrays.** Export from this module two derivations from the mark record —
the locked codes and the excluded codes, each as a `number[]` — so Task 2's request builder and its
tests consume one tested function rather than re-deriving the filter. These arrays are numeric
codes by construction; a card's displayed name never enters them.

**The request (D-15, Pitfall 3).** POST `/api/solve` through the api layer with a body of
`{ entry, free_transfers, horizon, max_transfers, locks, excludes }` where `locks` and `excludes`
come from Task 1's tested code derivations — numeric `player_code` values only. A card's displayed
name must never be turned into a lock string: the client always holds the exact code, and the
server's fuzzy name matching exists only for free-text input this UI does not have. Omit
`max_transfers` from the body when its input is empty rather than sending null-ish junk.

**In flight (D-15).** Disable the solve button, render an inline status line reading exactly
`Solving your transfers…` beside the pitch, and leave the pitch rendered and readable — never
replace it with a spinner. Disabling the button while a request is pending is also the client-side
brake that stops a user queuing repeated integer-programming solves.

**Ordering safety.** If a solve response can arrive after the user has changed marks and started
another solve, ignore the stale one — key the query or guard the state update so the displayed
squad always corresponds to the most recent request. A superseded response must never win.

**Failure.** Render `Couldn't solve: {message}. Check your inputs and try again.` extracting
`{message}` from the response's `detail` field when present and the status code otherwise, matching
the extraction vanilla uses on its own error paths.

**Response handling.** Branch on the response's `kind` discriminator. Only the `"transfers"` arm can
occur here — this UI never sends a null entry, per the view-only default resolved in 03-01 — but
handle the union exhaustively so the compiler enforces it rather than a runtime assumption.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/api/solve` | User-chosen locks, excludes and solver bounds cross into a server-side integer program |
| client state → request body | Card identity crosses from rendered UI into a request that selects real players |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-14 | Tampering | Locks and excludes sent as free-text names, resolved by the server's substring matcher | medium | mitigate | Task 1's derivations return numeric `player_code` arrays by construction, and Task 2's test asserts the serialised request body contains none of the marked players' display names — the server's name resolver is never exercised by this client |
| T-03-15 | Denial of Service (server CPU) | Repeated solves queued by a user clicking through a long-running integer program | medium | mitigate | The solve button is disabled while a request is in flight; the server's per-parameter solve cache makes an identical repeat free; the horizon and transfer inputs are bounded to the server's own limits so no oversized problem can be requested |
| T-03-16 | Tampering | A superseded solve response overwriting the displayed squad | low | mitigate | Task 2's ordering guard plus the explicit stale-response acceptance criterion |
| T-03-17 | Spoofing | An API key embedded client-side to reach the key-gated solve endpoint | high | mitigate | No key is read, stored or sent by any client code; the endpoint runs open when `FPL_API_KEYS` is unset and keying it is an operator concern belonging to PAID-02 |

<flagged_assumptions>
- **Solve results bar has no interval.** The UI-SPEC promises an optional p10–p90 range on the XI xP
  line; the endpoint returns no such fields. The bar shows `xi_xp` alone. If an interval is wanted
  there, it needs a backend change to `/api/solve`, outside this phase's contract.
- **Idempotency depends on the server cache.** The identical-second-solve truth is asserted against
  a mocked fetch returning the same body, which is what the server's per-parameter cache guarantees
  in practice. A pool refresh between two solves legitimately changes the answer; that is correct
  behaviour, not a violation.
- **Free-transfers estimate source.** The prefill comes from the API's own estimate, which
  `api/main.py` itself notes is inferred from transfer history because FPL only reveals the true
  figure to the manager's own login. A wrong prefill is the server's inference being wrong, not a
  UI defect — which is exactly why the input stays editable.
</flagged_assumptions>
