1. **`chips.json`'s `dgw_clubs` / `bgw_clubs` are integer counts, not arrays of club names.**
   Verified during planning from live `web/data/chips.json` and from `predict/export.py:197-198`
   (`"dgw_clubs": sum(1 for v in counts.values() if v > 1)` and
   `"bgw_clubs": len(all_teams) - len(counts)`). `03-RESEARCH.md`, `03-PATTERNS.md` and

   "reveal the affected clubs". The export cannot supply names. The timeline therefore marks a
   gameweek when the count is above zero and the popover reports the **count**. This is recorded
   as row 13 of this phase's PARITY-DEVIATIONS ledger (seeded by 03-01) — implement the count
   behaviour, do not invent club names.

2. **The live export currently has zero DGW and zero BGW gameweeks** (all 36 structure rows are
   `0`/`0`, gw 3 through 38). The all-plain timeline is the *normal* state, not a failure state —
   and it means the DGW/BGW paths need a second, hand-built fixture to be exercised at all.

3. **ROADMAP success criterion 3 says "default entry 6980093"; `03-CONTEXT.md` D-10 explicitly
   rejects auto-loading any real team.** CONTEXT.md is the later, authoritative artifact and the
   user's stated reason was direct ("would not want a random team to show up every time").

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/api/team/{entry}`, `/api/rate/{entry}` | User-supplied entry ID crosses into a server request that proxies the upstream FPL API |
| browser → `/data/chips.json` | Pipeline-authored `note` prose crosses into the DOM |
| URL → application state | `?entry=` and `?tab=` are attacker-controllable inputs on any shared link |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-05 | Denial of Service (upstream) | `/api/team/{entry}` and `/api/rate/{entry}` driven by a user-typed or URL-supplied entry ID | medium | mitigate | Numeric-only input with the server's own `min="1"` bound mirrored client-side; the Load team and rate requests are disabled while in flight; TanStack Query caches per entry so a repeat is free; the server's 1-hour pool cache and per-params solve cache remain the backstop |
| T-03-06 | Tampering | `?tab=` accepting an unrecognised value | low | mitigate | Unknown `?tab=` values fall back to the Squad default rather than rendering an unmounted panel or throwing |
| T-03-07 | Tampering | `chips.json`'s `note` and manager/team names rendered into the DOM | medium | mitigate | Every value renders as a JSX text node; `pairMoves` returns structured data rather than the HTML string vanilla built, removing the only place this phase was tempted to inject markup |
| T-03-08 | Information Disclosure | A loaded manager's squad or entry ID persisted to browser storage | low | mitigate | Task 1's storage grep gate; entry IDs live only in the URL, matching vanilla's own "nothing is stored" disclaimer |
| T-03-09 | Spoofing | An API key embedded in client code to reach the key-gated `/api/rate` and `/api/plan` endpoints | high | mitigate | No key is ever read or sent from the client — the endpoints run in open mode when `FPL_API_KEYS` is unset, and keying them is an operator concern belonging to PAID-02, outside this phase |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs **zero** packages. If one becomes genuinely necessary, halt and route it through the blocking package-legitimacy human gate before installing; `[ASSUMED]`/`[SUS]` verdicts are never auto-approvable |
</threat_model>
