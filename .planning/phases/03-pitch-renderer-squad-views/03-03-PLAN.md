<hard_bound>
**The rating endpoint returns a single best move, never an ideal squad.** Verified from
`api/main.py:384-403` during planning: `ideal = pick_squad(...)` is computed only to produce the
scalar `ideal_xi_xp`; `ideal["squad"]` is never put in the response body. The only per-player
suggestion is `best_move`, produced by a one-transfer solve, and it carries **names only** —
`{"sell": [name], "buy": [name], "xp_gain": number}` — with no `player_code`, no `position`, no
price.

Consequences you must design to, not around:
- Do not create a prop, type or fixture field named for an ideal squad's player list. There is no
  data to fill it and a component shaped that way is unbuildable.
- The diff is: the user's own `xi[]` (15 real rows) on the pitch, with at most one card marked out
  and at most one ghost card inserted.
- Building a true 15-versus-15 diff would require adding the ideal squad to the API response — a
  backend change explicitly outside this phase's "export and API consumed unchanged" contract.
  If that is ever wanted, it belongs in a later phase, not here.
</hard_bound>
