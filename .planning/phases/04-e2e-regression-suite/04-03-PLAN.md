Derive both variants from the normal capture by script (D-06: one deterministic transform, so all three scenarios share the same real player names and prices and cannot silently drift apart the way three hand-authored sets would).

Create `e2e/scripts/synthesize-variants.mjs`, a plain Node script using only `node:fs` and `node:path` (the repo's zero-dependency tooling convention), invoked as `node e2e/scripts/synthesize-variants.mjs`. It reads `e2e/fixtures/v1/normal/web-data/` and writes `e2e/fixtures/v1/blank/web-data/` and `e2e/fixtures/v1/dgw/web-data/`. It must never write into `normal/`. Every output must be deterministic: selections are made by sorting on a stable key, never by object iteration order and never by randomness, so a second run reproduces the same bytes.

Both variants need only a `web-data/` directory — plan 04-02's config points the blank and dgw servers at the normal set's `api/` through `FPL_FIXTURE_DATA_DIR`, because every surface D-09 scopes to these scenarios (the fixtures ticker, the chip timeline, the xP table) is a pure `/data` renderer that never calls the API.

Selection rule, stated once and reused: take the ticker rows from `normal/web-data/fixtures.json` sorted ascending by their `short` club code; the first six are the BLANK clubs, and the first four are the DOUBLE clubs. Record both resulting code lists verbatim in the MANIFEST so the specs can hardcode them.

Blank set — copy every file from `normal/web-data/` verbatim, then transform four:
- `fixtures.json`: for each blank club's row, replace the current gameweek entry's `fixtures` array with an empty array. Leave `xg_next`, `xgc_next` and `ease` untouched, and record in the MANIFEST that they are deliberately not recomputed and not asserted.
- `chips.json`: set the current gameweek's `bgw_clubs` to the blank club count, leave `dgw_clubs` at its captured value, and set `note` to the exact wording `predict/live.py`'s `_chip_note` produces for a blank week, with the gameweek and count substituted.
- `xp_table.json`: drop every row whose `team_short` is a blank club. This is what a real blank week produces — `_gw_pool` skips a club with no fixture entirely, so its players are absent from the export rather than present with a zero.
- `captains.json`: drop rows whose `team_short` is a blank club, preserving the surviving rows' order.

Double set — copy every file verbatim, then transform two:
- `fixtures.json`: for each double club's row, append a second entry to the current gameweek's `fixtures` array — a copy of the existing entry with `home` inverted and `opp` set to the next club in the double list (the last wraps to the first), keeping the original `fdr`. A cell must end up with two chips of the same difficulty and opposite venue.
- `chips.json`: set the current gameweek's `dgw_clubs` to the double club count and `note` to `_chip_note`'s exact double-week wording with the gameweek and count substituted.
- Leave `xp_table.json` and `captains.json` untransformed, and record in the MANIFEST that a real double week would raise those players' xP but that the double-set specs assert only the ticker and the timeline, so no synthetic xP inflation is introduced.

Fill the MANIFEST's "Synthesis rules" section with: the script path and invocation, the selection rule, the two club code lists, the per-file transform list above, the explicit list of values left untransformed and why, and the determinism guarantee (re-running produces byte-identical output, which is how the sets stay verifiable without being hand-editable).
  </action>
