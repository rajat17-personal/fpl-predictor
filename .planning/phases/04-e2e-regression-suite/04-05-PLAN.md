<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser form input → `/api/solve` body | user-controlled entry id, transfer counts, horizon and lock/exclude arrays |
| `/api/plan` → real multi-gameweek ILP | an unbounded-looking horizon knob reaches a solver |
| frozen entry picks → rendered squad | third-party-shaped data becomes page content |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-16 | Tampering | entry-id input reaching the API | medium | mitigate | Task 1 asserts the client guard fires no request for empty or non-numeric input, and that the server answers an unknown numeric id with its own 404 rather than a traceback — the ASVS V5 input-validation control for this phase |
| T-04-17 | Denial of Service | horizon and transfer-count knobs driving the ILP | medium | mitigate | Task 2 asserts the rendered inputs carry the same bounds the server's request model declares, so an out-of-range value cannot be submitted from the UI; the server still validates independently |
| T-04-18 | Tampering | a lock or exclude sent as a display name rather than a player code | medium | mitigate | Task 2 asserts the locked code appears and the excluded code is absent in the response, which only holds if the request carried numeric codes as `buildSolveRequest` intends |
| T-04-19 | Denial of Service | the real two-gameweek plan solve hanging a CI run | low | accept | The plan test raises only its own timeout; the global timeout stays low so any other hung test is still caught |
| T-04-20 | Repudiation | a solver change silently altering recommendations | medium | mitigate | The single pinned golden makes an optimal-tie flip visible as one failing test with a named re-pin point, rather than a silent recommendation change |
</threat_model>
