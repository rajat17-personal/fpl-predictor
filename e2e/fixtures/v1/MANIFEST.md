# E2E Fixture Set — v1

## Version and immutability

This is fixture contract **v1**. **v1 is never edited in place.** Every Playwright spec
in this phase (and later phases) hardcodes literal expected values (cell strings, row
order, a pinned solver golden — D-15) derived once from these files. If the contract
ever needs to change — a new field, a different trim, a re-capture at a different
gameweek — cut a **v2** directory alongside `v1/`, migrate specs deliberately, and leave
`v1/` untouched. Mutating `v1` in place would invalidate every hardcoded golden silently,
with no test failure pointing at the cause.

## Provenance

- **`normal/api/bootstrap-static.json`, `normal/api/fixtures.json`** — read directly
  from the locally cached `data/raw/live/{bootstrap-static.json,fixtures.json}`
  (never re-downloaded), then trimmed to the exact keys the API reads (see Trimming
  keep-lists below). Every element and every team row is kept; only fields are
  trimmed, never rows.
- **`normal/api/pools/gw{3..8}.json`** — one file per gameweek, each the real
  `predict.live._gw_pool(boot, fixtures, g, artifact)` output (full, untrimmed
  `boot`/`fixtures` in memory, real `models/artifacts/xp_model.joblib` inference at
  capture time) round-tripped through `DataFrame.to_json(orient="records")` ->
  `json.loads` -> `json.dump(indent=1)` so the files are line-diffable in review.
  This is the D-10 frozen prediction pool: fixture-mode `api/main.py` reads these
  files directly at request time and never re-runs model inference.
- **`normal/api/intervals.json`** — a verbatim copy of
  `models/artifacts/intervals.json` at capture time (p10/p90 residual bands).
- **`normal/api/entries/6980093/{picks_event2.json,summary.json,history.json}`** —
  fetched live, once each, from the official FPL API
  (`/entry/6980093/event/2/picks/`, `/entry/6980093/`, `/entry/6980093/history/`)
  in the same capture run as the bootstrap/fixtures read above, so `/api` and
  `/data` describe one coherent gameweek universe (D-07).
- **`normal/web-data/*.json`** — regenerated by `predict/export.py`'s own builders
  (`build_meta`, `build_table`, `build_captains`, `build_squad`, `build_ticker`,
  `build_chips`, `build_standings`, `build_leaders`) against the same captured
  `boot`/`fixtures`/pool as the `api/` directory above — not hand-authored, not
  copied from a stale `web/data/` snapshot.
- **`normal/web-data/watchlist.json`** — copied verbatim from `web/data/watchlist.json`.
  It has no export-builder (it's produced by `models/price.py`, a separate pipeline
  stage), so it is captured as-is rather than regenerated.

**`scoreboard.json` is intentionally absent.** Its absence is the real production
state that `frontend/src/routes/Scoreboard.tsx` distinguishes from a server failure
(no post-GW predictions have been scored yet for a freshly captured gameweek), and
the fixture set preserves that state rather than synthesizing a fake scoreboard.

**No `history/` directory is captured** — it is not part of the API/data contract
this phase's fixture seam serves.

## Trimming keep-lists

- **`bootstrap-static.json`** — top-level: `total_players`. `events`: `id`,
  `is_next`, `finished`, `deadline_time`. `teams`: `id`, `name`, `short_name`.
  `elements`: `id`, `code`, `web_name`, `team`, `element_type`, `now_cost`,
  `status`, `chance_of_playing_next_round`, `selected_by_percent`, `ep_next`,
  `news`.
- **`fixtures.json`** — per fixture: `event`, `team_h`, `team_a`, `kickoff_time`,
  `finished`, `team_h_difficulty`, `team_a_difficulty`.
- **`entries/6980093/picks_event2.json`** — `picks` (each keeping `element`);
  `entry_history` (keeping `bank`, `value`).
- **`entries/6980093/summary.json`** — `name`, `player_first_name`,
  `player_last_name`, `summary_overall_points`, `summary_overall_rank`,
  `summary_event_points` — see Task 1 policy below for what is scrubbed from
  this file specifically.
- **`entries/6980093/history.json`** — `chips` (each keeping `name`, `event`);
  `current` (each keeping `event`, `event_transfers`).

## Task 1 checkpoint decision: manager-field capture policy

**Verbatim answer: `scrub-names`.**

> Scrub the two manager name fields, keep the team name (recommended).

Applied to **`entries/6980093/summary.json` only** — no other file in this fixture
set is affected by this decision (`picks_event2.json` and `history.json` carry no
name fields and are captured verbatim regardless).

Concretely: `player_first_name` and `player_last_name` are written as empty strings
in the committed `summary.json`. The real team name (`name`) and every numeric
season figure (`summary_overall_points`, `summary_overall_rank`,
`summary_event_points`) are captured verbatim. At request time, fixture-mode
`api/main.py` builds the `manager.manager` display name from these two (now blank)
fields exactly as production code does — the result is an empty string, not a
placeholder substituted after the fact.

## Why the pool is JSON, not parquet

The pool files are JSON so that a zero-dependency Node script (the blank/DGW
variant-synthesis script planned for a later plan in this phase) can read every
fixture file without a Python or parquet-reading dependency. JSON also keeps every
frozen pool file line-diffable in code review, which a binary parquet file would not
be.
